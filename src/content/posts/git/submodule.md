在 Git 中，将一个仓库作为另一个仓库的子目录进行管理，主要有两种标准方式：**Git Submodule（子模块）** 和 **Git Subtree（子树）**。它们各有优劣，适用于不同的场景。

### 方案一：Git Submodule（子模块）

这是 Git 的原生功能，子模块是**父仓库对另一个独立仓库的引用**。父仓库只记录了子模块的**提交哈希值**，并不包含它的实际文件。

*   **适用场景**：适合**需要独立开发和频繁更新**的模块。比如团队共用的核心库，或仍在积极维护的第三方库。
*   **优点**：仓库边界清晰，子模块有完整的独立历史。
*   **缺点**：操作相对复杂，克隆主仓库后需额外步骤才能拉取子模块代码。

#### 操作步骤

**1. 添加子模块**
在主仓库根目录执行：
```bash
git submodule add <子仓库的URL> [存放的目录路径]
```
*   例如：`git submodule add https://github.com/user/common-lib.git libs/common-lib`。
*   执行后，Git 会做两件事：
    1.  在项目根目录生成一个 `.gitmodules` 文件，记录子模块的 URL 和本地路径，这个文件需要提交到版本库。
    2.  将子仓库克隆到指定目录，并将其当前状态记录为一个“提交”。
*   最后，提交这次更改：`git commit -m "添加 common-lib 子模块"`。

**2. 克隆包含子模块的项目**
*   **方法一（推荐）**：克隆时直接拉取所有子模块。
    ```bash
    git clone --recurse-submodules <主仓库URL>
    ```
*   **方法二**：如果已经克隆了主仓库，可以手动初始化和更新子模块。
    ```bash
    git submodule init
    git submodule update
    ```
    或者合并为一条命令：`git submodule update --init --recursive`。

**3. 更新子模块**
当子模块有更新时，进入子模块目录拉取最新代码：
```bash
cd libs/common-lib
git pull origin main  # 或你的目标分支
cd ../..
git add libs/common-lib
git commit -m "更新 common-lib 子模块到最新版本"
```

### 方案二：Git Subtree（子树）

它将子仓库的代码**直接复制**到父仓库的指定目录下，并合并为一个完整的提交历史。

*   **适用场景**：适合**希望简化管理，让所有代码都在一个仓库中**的场景。例如，将稳定的 UI 组件库或工具包嵌入到主项目中。
*   **优点**：对使用者透明，克隆主仓库后所有代码立即可用，无需额外操作。
*   **缺点**：会将子仓库的历史合并进来，可能使主仓库历史变得庞大；向子仓库上游贡献代码稍复杂。

#### 操作步骤

**1. 添加子树**
```bash
# 1. 先将子仓库添加为一个远程仓库（方便后续操作）
git remote add -f sub-repo <子仓库的URL>
# 2. 将子仓库的代码作为子树添加到主项目中
git subtree add --prefix=<本地目录路径> sub-repo <分支名> --squash
```
*   `--prefix`：指定子项目在主项目中的存放路径。
*   `--squash`（可选）：将子项目的完整历史压缩成一个提交，避免主仓库历史过于庞大。

**2. 更新子树**
当子仓库有更新时，将更新拉取到主项目中：
```bash
git subtree pull --prefix=<本地目录路径> sub-repo <分支名> --squash
```

**3. 推送子树修改**
如果你在子树的目录中做了修改，并希望将这些改动推送回子仓库的远程：
```bash
git subtree push --prefix=<本地目录路径> sub-repo <分支名>
```

### 总结与选择建议

| 特性 | Git Submodule (子模块) | Git Subtree (子树) |
| :--- | :--- | :--- |
| **代码存储** | 父仓库只存**引用** (commit ID) | 子项目代码**直接复制**到父仓库 |
| **克隆体验** | 需额外步骤 (`--recurse-submodules`) | **一键克隆**，所有代码立即可用 |
| **工作流复杂度** | 相对复杂，需理解子模块的独立状态 | 更简单直观，对普通开发者更友好 |
| **历史记录** | 完全独立，互不干扰 | 子项目历史**合并**到主项目，可能使主项目历史变大 |
| **适用场景** | 依赖项需**独立演进**、频繁更新 | 希望**统一管理**、简化工作流，依赖项相对稳定 |

**简单来说**：
*   如果你的子仓库需要**独立发展**，且你希望**明确区分**两个项目的提交历史，可以选择 **Submodule**。
*   如果你希望**所有代码都在一个仓库里**，让团队成员**克隆即用**，操作更简单，可以选择 **Subtree**。
