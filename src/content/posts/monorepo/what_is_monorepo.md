**Monorepo**（英文全称 **Monolithic Repository**，即“单一代码仓库”）是一种项目管理策略，指**将多个不同的项目、服务或包（Package）统一存放在同一个版本控制仓库（如 Git）中**。

为了帮你更直观地理解，可以对比传统的 **Multirepo（多仓库）** 策略：

- **Multirepo（多仓库）**：每个项目各占一个独立的 Git 仓库。比如“用户中心”一个仓库，“支付模块”一个仓库，“前端组件库”又一个仓库。
- **Monorepo（单仓库）**：把所有上述代码全部塞进**同一个** Git 仓库里，但在根目录下通过文件夹（`packages/` 或 `apps/`）进行物理隔离。

---

### 1. Monorepo 的核心特点
它绝不是“乱糟糟地把代码堆在一起”，而是**借助工具进行强约束的集中式管理**。典型特征包括：

- **统一的依赖管理**：整个仓库只有一个 `package-lock.json`（或类似锁文件），所有项目共用一套第三方依赖，极大减少了“版本冲突”和“重复安装”的问题。
- **统一的构建/测试流程**：一次命令（如 `npm run build`）可以按依赖顺序自动构建所有子项目。
- **严格的权限与边界**：虽然代码在一起，但通过工具（如 Nx、Turborepo）可以限制不同项目之间的引用，防止“乱引用”导致耦合。

---

### 2. 为什么大厂（Google、Meta、微软）都爱用？
Monorepo 能带来极其显著的工程效率优势：

- **原子化提交（Atomic Commits）**：当你修改了一个底层工具函数，需要同步修改 10 个上层业务项目时，在一个仓库里只需**一次提交**即可完成全部修改，不会出现“A 项目改了接口，B 项目忘记适配”导致线上故障的情况。
- **极致的代码复用**：共享组件或工具函数可以直接 `import`，无需发布到私有 NPM 仓库再下载，调试时甚至可以直接修改源码即时生效。
- **跨项目重构**：借助 IDE 和工具，重命名一个函数名可以瞬间重构整个仓库里的所有引用，安全且高效。

---

### 3. Monorepo 的致命缺点（为什么小团队不敢用？）
- **仓库体积巨大**：随着时间推移，Git 历史可能变得极其庞大，克隆一次需要很长时间（Google 的仓库甚至达几十 TB）。
- **工具链复杂**：原生 Git 和 npm 无法高效处理大仓库，必须引入 **Bazel**、**Nx**、**Turborepo** 或 **Rush** 等专业构建工具来实现“增量构建”（只构建改动过的项目）和“任务编排”。
- **权限管理困难**：虽然代码在一起，但你可能只想让 A 团队改 A 文件夹，这需要借助 `CODEOWNERS` 文件或 Git 子模块进行精细控制，比较繁琐。

---

### 4. 什么时候该用 Monorepo？
- **适合**：微服务/微前端架构众多、需要大量共享业务逻辑或 UI 组件库、团队成员超过 50 人、追求极致工程效率的大型项目。
- **不适合**：业务逻辑完全独立、无任何代码交集、团队只有 3~5 人且维护成本极低的小型外包项目。

---

### 5. 当下主流的 Monorepo 生态工具
如果你打算尝试，目前最火的是：

- **Turborepo**（Vercel 出品）：配置极简，构建缓存能力极强，适合 JavaScript/TypeScript 生态。
- **Nx**（Nrwl 出品）：功能最强大，支持 Angular、React、Node.js，甚至 Java 和 .NET。
- **Rush**（微软出品）：适合大型企业级，严格的依赖版本控制。
- **Lerna**（经典老牌）：现在常与 Turborepo 配合使用。
